## Search Premise

The last recovery, release, route-book, and evidence-desk attempts failed because the founder controlled only a file, mandate, or service process while incumbents controlled trust, source truth, payment decisions, or technical authority. This round tests a different control object: exact software package namespace and publishing rights, with dependent-company prepayments before closing. The buyer is not paying for a dashboard, report, or generic dev agency. The buyer pays because a specific production dependency must keep receiving releases after the maintainer exits.

Internal scoring caps applied here only:

- cap below 82 without concrete 6-month control proof;
- cap below 85 if one vendor contract, equipment purchase, consultant, or hire can copy it;
- cap below 87 if CAC, payback, margins, cash conversion, or owner earnings are weak;
- cap below 87 if dependent on vague partnerships/goodwill/interviews;
- cap below 82 if clinical/legal/patient/regulated-data authority is unresolved.

## Lead Candidate: MaintainerExit Package Continuity Buyout

### Buyer

B2B SaaS companies, software-product teams, agencies with retained product clients, DevOps teams, API-heavy startups, and vertical software vendors that already rely on a specific small but production-relevant open-source package, SDK wrapper, parser, connector, CLI tool, protocol adapter, or framework plugin.

### Acute Trigger

The maintainer is retiring, unresponsive, burned out, or explicitly wants out while dependent companies face a current runtime, framework, API, security, build, browser, package-manager, or buyer-procurement update. The buyer does not need generic open-source support; it needs the exact package it already uses to keep publishing trusted releases under the known namespace.

### Control Point

Signed package-rights option or transfer covering:

- GitHub/GitLab repository administration;
- package-registry namespace and publishing rights for npm, PyPI, Maven, Composer, Packagist, Docker Hub, Terraform Registry, or similar where relevant;
- release-signing or maintainer keys rotated through a secure handoff;
- domain/docs/site and issue tracker;
- changelog, CI, test suite, dependency map, security advisory history, open pull requests, and contributor notes;
- maintainer endorsement and transfer announcement;
- sponsor/support contact list where legally transferable;
- prepaid dependent-company LTS or continuity contracts before meaningful seller payment.

### 60-Day Proof

1. One maintainer signs an option over a package with meaningful production dependents and clean transfer authority.
2. Registry transfer or co-maintainer handoff is rehearsed or completed without publishing-risk ambiguity.
3. Eight dependent companies sign 12-month continuity/LTS contracts or prepaid support blocks totaling at least 60,000 PLN before closing cash is paid to the maintainer.
4. One named senior contractor reviews the repo, CI, tests, release process, dependency risk, and first scoped maintenance plan.
5. First maintenance release, security patch, runtime/framework compatibility release, or clean no-go advisory ships under the controlled namespace.
6. Scope excludes regulated, crypto/security-critical, payment-processing, health/patient, destructive-infra, or classified packages in the first POC.

### Economics

Charge dependent companies 2,500-12,000 PLN per year for package continuity, LTS patch access, supported-version notices, priority issue triage, buyer-safe maintenance notes, and optional private compatibility patches. A package with 15 paying dependents at 6,000 PLN/year creates 90,000 PLN ARR. Seller payout is an earnout from collected contracts, not speculative purchase. Gross margin can stay above 65% if only packages with small, bounded maintenance surfaces and existing tests are accepted.

### Copy Risk

HeroDevs, Tidelift, Snyk, GitHub, OpenCollective, foundations, dev agencies, security firms, and larger user companies can offer open-source support or fork the code. The defense is package-specific control: once the startup controls the trusted namespace, release channel, maintainer endorsement, issue history, and prepaid support stream, competitors cannot instantly publish trusted official releases for that package. They can fork, but the buyer's production dependency and procurement evidence usually prefer the recognized package lineage.

### Why It Is Not A Service, Report, App, Dashboard, Marketplace, Or Broker

The business does not sell generic coding hours, dependency reports, vulnerability scans, dashboards, introductions, or a marketplace of maintainers. It buys or options the exact package continuity asset and closes only when dependent companies prepay for that package's official continuity stream.

### Legal And Provider Boundaries

The startup does not provide legal advice, security certification, formal penetration testing, software warranty, regulated compliance attestation, malware analysis for unknown packages, escrow, insurance, or fiduciary custody of community funds. Counsel reviews IP/assignment/license issues where needed. Security reviewers handle vulnerability-sensitive releases. Customers remain responsible for their own dependency risk, code integration, deployment, testing, and production acceptance. Reject packages with unclear maintainer authority, disputed IP, malware, abandoned but widely security-critical auth/crypto/payment code, healthcare/patient-data libraries, license contamination, sanctions/export-control issues, toxic community disputes, or no paying dependent companies.

### Duplicate Risk

This is not OneStack Critical Connector Lockbox or Retail EDI continuity. Those buy installed customer-specific connectors and support books. MaintainerExit controls a public package namespace and release channel used across multiple dependent companies, with no customer-specific ERP cleanup unless separately contracted. It is not DORA, REDBlocked, BioSignal, HeritageDoor, TraceFaktura, PromoLeak, CBAM, Data Act Machine Data Liberation, GreenTender EPREL, BatteryFit, Supplement Stack, HeatQuiet, RAGProbe, AIQ, AppExchange, or any recovery/evidence desk.
